# home.ss.ge — реверс-инжиниринг API (для оформления в MCP)

Разобрано 2026-09-06. Всё ниже проверено живыми запросами, не выведено из кода.
Публичного/документированного API нет, swagger закрыт (404). Схема восстановлена из
сгенерированного openapi-generator TS-клиента в бандлах Next.js + эмпирической проверкой.

## 1. Как всё устроено

| | |
|---|---|
| Фронт | Next.js (`buildId` меняется при деплое), страница `/real-estate` |
| API gateway | `https://api-gateway.ss.ge` |
| Базовый путь | `/v1/...` (один эндпоинт на `/v3/`). **Не** `/api/v1/` — это 404 |
| Авторизация | `Authorization: Bearer <JWT>` |
| Локаль | заголовок `accept-language: ru | en | ka` — переводит **данные**, не только UI |
| robots.txt | запрещает только `/ka|en|ru/user`. API-пути не запрещены |

### Токен

Анонимный, уровня приложения (OAuth2 `client_credentials`, `client_id=ssweb`,
issuer `https://account.ss.ge`, TTL **1 час**, без `sub` — пользователя не представляет).
Scopes: `real_estate`, `house_api`, `statistics`, `files`, `banners`, …

Два способа получить:

1. **Предпочтительный для MCP.** Забрать готовый токен со страницы — сайт сам кладёт его
   каждому посетителю в `__NEXT_DATA__`:
   `props.pageProps.credentialsToken` в HTML любой страницы `https://home.ss.ge/ru`.
2. `POST https://account.ss.ge/connect/token` с `grant_type=client_credentials` и парой
   `client_id`/`client_secret`, захардкоженной в публичном JS-бандле.

Способ (1) строго лучше: не требует хранить чужой секрет в конфиге MCP, не ломается при
ротации секрета и точно повторяет поведение обычного браузера. **Кешировать токен на ~55 мин**
и обновлять по 401.

> Секрет из способа (2) лежит в открытом бандле, но в репозиторий/конфиг его класть не нужно —
> способ (1) полностью его заменяет.

## 2. Эндпоинты, которые нужны для поиска недвижимости

Всего в бандле 320 путей `/v1/*` (RealEstate 82, ManageRealEstate 28, PaidService 33,
Account 21, House 16 — новостройки, и т.д.). Для read-only MCP релевантны эти:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/RealEstate/LegendSearch` | Основной поиск. Пагинация, **есть `createDate`** |
| POST | `/v3/RealEstate/legend-search-count` | Счётчики результатов (`cardCount`, `applicationCount`) |
| POST | `/v1/RealEstate/MapSearch` | **Весь** результат одним ответом: id + цена + координаты. Без пагинации |
| GET | `/v1/RealEstate/MapSearchByIds?applicationIds=1,2,…` | Полные карточки по списку id (батч ≤ ~300) |
| PUT | `/v1/RealEstate/details?applicationId=&currencyId=&updateViewCount=false` | Полная карточка: удобства, координаты, кадастр, `viewCount` |
| GET | `/v1/RealEstate/LocationChain` | Гео-справочник: город → район → микрорайон → улица, с координатами (~660 КБ) |
| GET | `/v1/RealEstate/visibleCities` | Список городов |
| GET | `/v1/RealEstate/currency-rate` | Курс USD/GEL |
| GET | `/v1/RealEstate/similar`, `/similarities` | Похожие объявления |
| GET | `/v1/RealEstate/phone-number` | Телефон по объявлению |
| GET | `/v1/Home/healthy`, `/v1/Home/Env` | Health + дата индекса |

`POST` — тело JSON. `GET`/`PUT` — параметры в query. `details` именно **PUT**, не GET.

## 3. Тело фильтра (общее для LegendSearch / MapSearch / count)

```jsonc
{
  "realEstateType":     5,          // int, см. §4
  "realEstateDealType": 4,          // int, см. §4
  "cityIdList":         [95],       // ICollection<int> — ТОЛЬКО массив
  "subdistrictIds":     [3, 47],    // ICollection<int>
  "streetIds":          [1195],     // ICollection<int>
  "municipalityId":     12,         // int
  "rooms":              [2, 3],     // ICollection<int>
  "bedroomsCount":      [1, 2],     // ICollection<int>
  "areaFrom": 50, "areaTo": 90,     // м²
  "currencyId": 2,                  // 1 = GEL, 2 = USD
  "priceType":  1,                  // 1 = цена целиком, 2 = цена за м². ОБЯЗАТЕЛЕН для цены
  "priceFrom": 500, "priceTo": 900,
  "subwayStation": "isani", "subwayStationDistance": 15,   // минут пешком
  "searchString": "…",
  "order": 1,                       // см. §4
  "page": 1, "pageSize": 30,        // только LegendSearch
  "advancedSearch": { "elevator": true }   // ОБЪЕКТ, не JSON-строка
}
```

### Грабли, проверенные на живых запросах

1. **`priceType` обязателен.** Без него `priceFrom`/`priceTo` молча игнорируются —
   вернётся полная выдача. Проверено: 32 710 → 5 882 результата после добавления `priceType`.
2. **`districtIds` не существует.** Сайт кладёт его в URL, но DTO его игнорирует
   (счётчик не меняется). Фильтровать по району можно только через `subdistrictIds`,
   разворачивая район в список микрорайонов по `LocationChain`.
3. **Массивы обязаны быть массивами.** `"cityIdList": "95"` → 400. Сайт местами шлёт
   строки через запятую — это остаток старого контракта, сейчас не работает.
4. **`advancedSearch` — объект.** В коде сайта он `JSON.stringify`-ится; API такое отвергает (400).
5. **Неизвестные поля молча игнорируются** (обычный ASP.NET DTO). Опечатка в имени фильтра
   не даёт ошибки — она даёт неотфильтрованную выдачу. Для MCP это главный источник
   тихо неверных ответов: валидировать имена на своей стороне.
6. **`pageSize` > 30 → HTTP 401** (не 400 и не обрезка). Жёсткий потолок — ровно 30.
7. **`totalCount` в ответе `LegendSearch` всегда 0.** Мёртвое поле. Считать только через
   `/v3/.../legend-search-count`.
8. Ошибки валидации всегда содержат бесполезное `"request": ["The request field is required."]` —
   смотреть надо на соседние ключи `$.<поле>`, они называют ожидаемый .NET-тип.

## 5. Три счётчика, и они не сходятся

Для фильтра «аренда квартир, Сабуртало»:

| Источник | Значение |
|---|---|
| `legend-search-count` → `cardCount` | 15 046 |
| `legend-search-count` → `applicationCount` | 50 197 |
| `MapSearch` → длина массива | 23 337 |

`cardCount` — карточки после схлопывания дублей (`similarityGroup`), `applicationCount` —
сырые объявления, `MapSearch` — объекты, у которых есть координаты. Ни одно не является
«числом уникальных квартир». MCP должен отдавать их раздельно и с пояснением, а не выбирать
одно и выдавать за истину.

Пагинация `LegendSearch` идёт вглубь примерно до `cardCount / 30` страниц, дальше пустые
страницы. То есть постранично достаётся именно `cardCount`, а не `applicationCount`.

## 6. Две стратегии выборки — и чем платим

**A. Постранично `LegendSearch`** — 30 объектов на запрос. `cardCount` 5 736 → 192 запроса.
Медленно, зато в карточке есть **`createDate` — реальная дата публикации**.

**B. `MapSearch` + `MapSearchByIds`** — весь набор id одним запросом, потом карточки
батчами по ~200–300. Те же 5 736 объектов ≈ 1 + 25 запросов, в 7 раз меньше.
**Но `MapSearchByIds` возвращает `createDate = 0001-01-01`** (не заполнено) — свежесть теряется.
`orderDate` есть, но это дата последнего платного поднятия, а не публикации: у всех
верхних объявлений она равна «сегодня».

Практический вывод для MCP: B — для «покажи всё на карте / посчитай / отфильтруй по цене»,
A — везде, где пользователя интересует «что нового» или возраст объявления. Смешивать нельзя,
иначе получится ровно тот же класс ошибки, что с недатированными карточками korter.

`MapSearch` не имеет потолка: без фильтров он отдаёт **144 046 объектов одним ответом на 35 МБ**.
MCP обязан ставить свой предохранитель (требовать город + тип сделки, иначе отказ).

## 7. Прочее

* Троттлинга не замечено: 12 запросов подряд за 0.4 с — все 200. Тем не менее для MCP
  разумно самоограничение ~1–2 rps и честный User-Agent.
* `MapSearchByIds` не сохраняет порядок входных id — сопоставлять по `applicationId`.
* URL длиннее ~4 800 символов → 500. Отсюда потолок батча ~300 id.
* Ссылка на объявление: `https://home.ss.ge/ru/недвижимость/<detailUrl>`, где `detailUrl`
  приходит в карточке.
* Картинки — `https://static.ss.ge/...`; в выдаче отдаются `_Thumb.jpg`.
* Цены приходят сразу в обеих валютах: `priceGeo`, `priceUsd`, `unitPriceGeo`, `unitPriceUsd` —
  конвертировать самим не нужно.
* `/v1/House/*` — отдельный раздел новостроек (проекты, планировки, застройщики).
  Не трогал, но структура симметричная.

## 8. Что предложить наружу в MCP

`search` (фильтр → карточки, стратегия A/B параметром) · `count` (три счётчика с пояснением) ·
`listing` (полная карточка по id) · `geo` (дерево локаций, резолв названия → `subdistrictIds`) ·
`similar`. Плюс на входе: раскрытие района в микрорайоны, валидация имён фильтров,
авто-подстановка `priceType`, кеш токена и `LocationChain`.
